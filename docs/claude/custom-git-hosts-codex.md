## Verdict

**Partial.** Omnigent is not limited to cloning from `github.com`: a long-lived `omni host` is forge-neutral because it starts runners in an already-existing local checkout, and the normal managed/disposable launcher accepts and passes through arbitrary `https://...` or `git@...:...` repository URLs. A public custom-host repository can therefore clone today, and a private one may clone when the managed image's generic `GIT_TOKEN`/`GIT_USERNAME` helper and injected environment match that host. This is not first-class custom-host support, however: there is no git-host/provider object tying together host identity, per-host credentials, API base URL, CLI/MCP behavior, and policy. That missing provider/host abstraction—especially above raw Git transport for PRs, issues, and repository metadata—is the single biggest blocker. Managed sandboxes expose the gap during provisioning and clone; long-lived hosts can bypass that part by being pre-cloned but still inherit the GitHub-specific API/tooling assumptions.

## How git hosting works today

1. **Connect and workspace selection differ by host lifetime.** A managed session may use `workspace` as a repository URL with an optional `#branch`; an external/long-lived host must use an absolute path already present on that host (`omnigent/server/schemas.py:1240-1260,1341-1386`). When a long-lived `omni host` receives a launch frame, `HostConnection._handle_launch` checks that the workspace is an existing directory and spawns the runner there; it does not clone (`omnigent/host/connect.py:1029-1078`).

2. **Login identity and repository credentials are separate.** GitHub login exchanges the authorization code, uses the returned access token only to resolve a verified email, then mints an Omnigent session JWT (`omnigent/server/routes/auth.py:197-203,250-289,339-345,679-713`). That JWT contains only `sub`, `iat`, `exp`, and `provider`; no upstream OAuth token is retained in it (`omnigent/server/oidc.py:53-83`). Git access instead comes from the host/deployment environment. `GIT_TOKEN` and `GIT_USERNAME` are explicit host-to-runner passthrough variables, and the code says a laptop owner exports them while a managed deployment injects them (`omnigent/host/connect.py:415-455,499-550`). Thus the GitHub login token is **not** reused as `GIT_TOKEN`.

3. **Managed URL intake is provider-neutral.** `SessionCreateRequest` validates managed workspaces through `parse_repo_workspace` and rejects repository URLs for external hosts (`omnigent/server/schemas.py:1341-1386`). The parser accepts only `https://<host>/<path>` and scp-style `git@<host>:<path>`, validates the basic shape/branch/directory name, removes the optional fragment, and returns the remaining URL unchanged. It neither compares the host with `github.com` nor rewrites it (`omnigent/server/managed_hosts.py:438-450,482-549`). The create route parses the URL again, preserves the raw value for relaunch, and schedules background managed provisioning (`omnigent/server/routes/sessions.py:14420-14438,14472-14474,14572-14627`).

4. **The normal managed launcher performs a plain Git clone.** Managed provisioning passes `repo.url`, `repo.branch`, and `repo.repo_name` unchanged into `launcher.start_host` (`omnigent/server/managed_hosts.py:1918-1946`). The default exec-model launcher creates `$HOME/workspace` and runs the shell-quoted equivalent of `git clone [--branch BRANCH --single-branch] -- URL DEST` (`omnigent/onboarding/sandboxes/base.py:285-301,320-389`). Only after the clone does it start `omnigent host` (`omnigent/onboarding/sandboxes/base.py:302-317`). The clone command does not install a helper or inject a credential. The managed-host contract instead relies on the host image's Git credential helper when the sandbox environment carries `GIT_TOKEN` (`omnigent/server/managed_hosts.py:1748-1753`); provider config can inject server environment variables such as `GIT_TOKEN` into each sandbox (`omnigent/server/managed_hosts.py:799-824,863-900`).

5. **Later agent Git operations inherit the same ambient pair.** Once the host is running, `_build_runner_env` copies present allowlisted credentials into the runner. The comment explicitly connects `GIT_TOKEN`/`GIT_USERNAME` to the image helper for later fetch/push, not only launch-time clone (`omnigent/host/connect.py:415-455,499-550`). This is one global pair, not a per-host credential registry. Separately, an agent spec can configure the secretless credential proxy: it resolves secrets from an environment variable, file, or command in the trusted parent and binds each rewrite to an exact host (`omnigent/inner/datamodel.py:377-450`; `omnigent/inner/credential_proxy.py:103-153,156-209`). That generic proxy is not in the managed pre-host clone path.

6. **Repository APIs are delegated; Omnigent has no first-class in-process GitHub repository client in the inspected paths.** The only direct GitHub HTTP call found is the login email lookup above. PRs, issues, and repository metadata are instead available to the agent through a configured external MCP server or agent-issued `gh` commands. `ServerMcpPool` is provider-neutral: it discovers tools from `spec.mcp_servers` and forwards calls to the named MCP connection (`omnigent/server/mcp_pool.py:146-240,349-360`), while session routes create/update arbitrary MCP server declarations (`omnigent/server/routes/session_mcp_servers.py:90-168,308-317`). The GitHub policy describes GitHub MCP and `git`/`gh` shell calls as its two surfaces (`omnigent/policies/builtins/github.py:1-20`), classifies PR/issue operations and `gh api`, and returns policy decisions; it does not execute HTTP or launch `gh` itself (`omnigent/policies/builtins/github.py:383-428,504-534,543-605,729-800,1076-1106`).

7. **Agent egress is configurable, but only default-deny when enabled.** Non-empty `egress_rules` start an HTTP(S) proxy; requests that match no rule are rejected (`omnigent/inner/datamodel.py:614-626`; `omnigent/inner/egress/rules.py:1-16,178-209`). The rule language accepts arbitrary exact/wildcard hosts and path globs, so its examples do not limit it to GitHub (`omnigent/inner/egress/rules.py:68-121,129-175`). A self-hosted destination on a private address also needs the existing `egress_allow_private_destinations` opt-in for agent traffic (`omnigent/inner/datamodel.py:627-650`). This inner egress/credential proxy starts with the runner; it is not shown wrapping the earlier managed `git clone`.

## Existing extension seams

- **Generic repository identity and clone:** `parse_repo_workspace` preserves an arbitrary HTTPS or scp-style SSH host (`omnigent/server/managed_hosts.py:508-549`), and the default launcher passes it to ordinary `git clone` (`omnigent/onboarding/sandboxes/base.py:320-389`). `SandboxLauncher.materialize_workspace` is already an override point for providers that resolve/cache repositories differently (`omnigent/onboarding/sandboxes/base.py:320-349`).
- **Provider-neutral long-lived hosts:** external sessions operate on an existing absolute directory and never need Omnigent to understand its remote (`omnigent/server/schemas.py:1341-1386`; `omnigent/host/connect.py:1029-1078`).
- **Manual runner environment extension:** operators can name additional host-to-runner variables through `OMNIGENT_RUNNER_ENV_PASSTHROUGH`; `_build_runner_env` forwards those named values (`omnigent/host/connect.py:458-463,499-550`). This could manually carry a CLI host variable, but it is not a modeled git-host setting.
- **Arbitrary egress hosts:** rule parsing/matching is host-generic, and private destinations have an explicit opt-in (`omnigent/inner/egress/rules.py:68-121,129-209`; `omnigent/inner/datamodel.py:614-650`).
- **Per-host secretless credentials:** unlike the single ambient `GIT_*` pair, credential-proxy entries are host-bound and can source a secret from env/file/command (`omnigent/inner/datamodel.py:377-450`; `omnigent/inner/credential_proxy.py:103-209`). The `git_https` preset takes explicit targets and an overridable username (`omnigent/spec/parser.py:1601-1635`). `gh_basic` also accepts explicit targets, though its API-host heuristic remains GitHub-shaped (`omnigent/spec/parser.py:1638-1685`).
- **Provider-neutral MCP transport:** the server can connect and forward tools to arbitrary configured MCP servers (`omnigent/server/mcp_pool.py:146-240,349-360`). A Forgejo/Gitea/GitLab/Bitbucket MCP integration can therefore plug into transport without adding a GitHub REST client to Omnigent.
- **A design precedent, but no git analog:** LLM onboarding exposes configurable `api_base` fields for Azure and Databricks (`omnigent/onboarding/providers/__init__.py:603-627,657-675`). No corresponding git-host record joins clone URL, API base, credentials, CLI, egress, and policy. The current Copilot executor has token selection but no `GH_HOST` (`omnigent/inner/copilot_executor.py:44-48,96-99,289-313`).

## What custom-host support would require

1. **Tier A — GitHub Enterprise; low-to-medium effort/risk (cheapest full integration).** Raw clone is already generic, so the work is mainly configuration consistency around the same GitHub API model.

   - **Onboarding/config:** introduce one canonical GitHub host configuration containing web/git host, API base, optional SSH/custom-port settings, and login independence. Carry it through managed config and session provisioning in `omnigent/server/managed_hosts.py` and `omnigent/server/schemas.py`; add a git-host onboarding peer rather than putting it in the LLM-only `omnigent/onboarding/providers/__init__.py`.
   - **Token/credentials:** replace or supplement the single global pair with host-keyed credentials while retaining it as a compatibility default. Wire the Enterprise CLI token/host variables through `omnigent/host/connect.py`; generate explicit host bindings through `omnigent/spec/parser.py`, `omnigent/inner/datamodel.py`, and `omnigent/inner/credential_proxy.py`. Ensure the pre-host managed clone receives the same selected credential via `omnigent/server/managed_hosts.py` and the launcher/image contract in `omnigent/onboarding/sandboxes/base.py`.
   - **Clone:** no base-command rewrite is required for supported HTTPS/scp-style URLs. Extend `parse_repo_workspace` in `omnigent/server/managed_hosts.py` only if `ssh://`, custom SSH ports, or provider canonicalization are requirements.
   - **Host API/tools:** set the configured host/API base for `gh` and any GitHub MCP server. Generic MCP transport in `omnigent/server/mcp_pool.py` and `omnigent/server/routes/session_mcp_servers.py` can remain; the configuration producer must supply the Enterprise endpoint.
   - **Policy:** parameterize `github.com`, URL parsing, and allowed API host in `omnigent/policies/builtins/github.py` instead of adding a second GitHub-shaped policy.
   - **Egress:** derive or validate rules for both the Enterprise git/web host and API host in `omnigent/spec/parser.py`; surface the existing private-destination opt-in for intranet installations.
   - **Login (optional):** if users must also sign in through GitHub Enterprise, parameterize the GitHub OAuth branch in `omnigent/server/oidc.py` and `omnigent/server/routes/auth.py`. Do not couple that token to repository access.

2. **Tier B — Forgejo/Gitea; medium-to-high effort/risk.** Git transport can reuse today's clone path, but first-class PR/issue/metadata support needs an adapter because the API and tool vocabulary are not GitHub's.

   - **Onboarding/config:** define a provider-neutral `GitHostConfig` plus a Forgejo/Gitea implementation (new modules under `omnigent/onboarding/` or a focused new `omnigent/git_hosts/` package), then reference it from `omnigent/server/schemas.py` and `omnigent/server/managed_hosts.py`. Model web host, API base/path, version/capabilities, and SSH form separately.
   - **Token/credentials:** add per-host clone and API credentials with provider-selectable username/scheme. Reuse the generic credential proxy in `omnigent/inner/datamodel.py`, `omnigent/spec/parser.py`, and `omnigent/inner/credential_proxy.py`; update `omnigent/host/connect.py` and managed launcher injection so the same host mapping is available both before and after host startup.
   - **Clone:** preserve `omnigent/onboarding/sandboxes/base.py` for normal HTTPS/scp SSH. Expand `parse_repo_workspace` in `omnigent/server/managed_hosts.py` for any required Forgejo/Gitea URL forms, custom ports, or certificate/SSH configuration.
   - **Host API:** add a Forgejo/Gitea adapter for repositories, PRs, issues, comments, and metadata. It can be a supported provider MCP server using the existing `omnigent/server/mcp_pool.py`, or a provider-neutral built-in façade registered through `omnigent/tools/builtins/__init__.py`; either choice is a new abstraction because no in-process GitHub repo adapter exists to extend.
   - **Policy/tools:** add a peer such as `omnigent/policies/builtins/forgejo.py` that understands the selected MCP/CLI operations and custom-host URL identities. Do not stretch `omnigent/policies/builtins/github.py` to classify a different API. Package or verify the chosen Forgejo/Gitea CLI/MCP runtime in managed images.
   - **Egress:** generate explicit rules for git/web/API hosts and expose `egress_allow_private_destinations` where the installation is reachable only on private addressing.

3. **Tier C — GitLab/Bitbucket; high effort/risk (largest semantic change).** Reuse Git transport, sandbox launch, generic MCP transport, egress, and low-level credential primitives, but implement separate provider adapters rather than treating these services as alternate GitHub base URLs.

   - **Onboarding/config:** extend the new provider-neutral host model with GitLab and Bitbucket variants in the proposed `omnigent/git_hosts/` package and connect it to `omnigent/server/schemas.py`/`omnigent/server/managed_hosts.py`.
   - **Token/credentials:** model provider-specific clone/API schemes and per-host tokens through `omnigent/host/connect.py`, `omnigent/spec/parser.py`, `omnigent/inner/datamodel.py`, and `omnigent/inner/credential_proxy.py`; keep login credentials separate.
   - **Clone:** retain `omnigent/onboarding/sandboxes/base.py` where standard Git URLs suffice, extending `omnigent/server/managed_hosts.py` only for additional URL grammars and canonical project identity.
   - **Host API:** implement separate GitLab and Bitbucket adapters (provider MCP integrations or a neutral built-in façade) for projects/repositories, merge/pull requests, issues, comments, pagination, and metadata. Do not force nested GitLab namespaces or Bitbucket workspace identity into the GitHub policy's two-segment `owner/repo` model.
   - **Policy/tools:** add provider peers to `omnigent/policies/builtins/github.py` that understand each API, MCP prefix, and chosen CLI; register any built-in façade in `omnigent/tools/builtins/__init__.py` and continue using `omnigent/server/mcp_pool.py` for external integrations.
   - **Egress:** derive web/git/API allowlist entries per provider in `omnigent/spec/parser.py`, including the existing private-destination setting for self-hosted GitLab.

## Open questions

- The actual managed-image Git credential helper is installed outside `omnigent/`; this bounded Python review could not verify its exact `GIT_USERNAME` default, host selection, certificate behavior, or whether one token can authenticate every targeted forge.
- `SandboxLauncher.start_host` is the default exec-model path, but entrypoint-style providers such as Kubernetes can override it. Their provider-specific clone/auth behavior was not opened under the file cap.
- The Python backend does not establish whether each managed image includes `gh` or another provider CLI, nor which GitHub MCP server—if any—is present in default agent bundles. Those bundle/image locations were outside scope.
- Reachability of an intranet forge during the pre-host managed clone depends on each sandbox provider's network, DNS, custom-CA, and SSH-host-key setup. The inner runner egress settings do not answer that earlier provisioning question.
- Product scope is unresolved: one deployment-wide custom host versus multiple simultaneous hosts; clone-only support versus PR/issue parity; and whether the forge must also serve as the Omnigent login provider. Those choices materially change the configuration and adapter design.
